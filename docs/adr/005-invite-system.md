# ADR-005: Invite-Gated Signup and Administrative User Management

**Date:** June 2026  
**Status:** Accepted

## Decision
We will enforce an invite-only registration system for new user accounts, alongside administrative controls to manage member roles and account states. This is implemented via:
1. **Single-Use Invite Tokens:** Cryptographically secure UUID tokens generated by admins, expiring in 72 hours, and stored in `invite_tokens` table.
2. **Encoded Redirect State:** Passing the chosen display name and invite token directly inside the `redirectTo` query parameter of `signInWithOAuth` (e.g., `/auth/callback?state=token:display_name`) to guarantee data is preserved through the Supabase/Google redirect loop.
3. **Replay & Fraud Protection:** Validating the token in `/auth/callback` on new signups. If invalid or missing, the user is signed out, and their auth account is deleted from `auth.users` via the service role client.
4. **JWT-based RLS Policies:** Restricting access to `invite_tokens` and `audit_log` using JWT custom claims `(auth.jwt() -> 'app_metadata' ->> 'user_role') = 'admin'` to prevent database subquery loops and table lock recursion.
5. **Real-time Deactivation:** Querying the database in middleware for authenticated requests to check if `is_active = false`. If a user is deactivated, the middleware signs them out and redirects them to the homepage with a deactivation notice.

## Reason
1. **Club Exclusivity:** As a university anime club member portal, self-registration must be disabled. Directing signups through invite link redemption ensures only invited members can register.
2. **Supabase State Preservation Limitations:** Supabase's `queryParams` option in `signInWithOAuth` does not reliably forward the custom OAuth `state` parameter back to the client callback. Appending it to the `redirectTo` URL ensures it is preserved.
3. **Preventing Auth Account Pollution:** Supabase Auth automatically creates a user in `auth.users` upon first Google login. By catching unauthorized signups in `/auth/callback`, logging them out, and deleting their account using the service role admin client, we prevent untrusted Google accounts from polluting our database.
4. **Preventing RLS Infinite Recursion:** RLS policies that query other tables (e.g., checking role by doing `exists (select 1 from public.users)`) can trigger infinite recursion and table locks in Postgres. Accessing the custom role claim directly from the signed JWT via `auth.jwt()` resolves this issue safely at no database cost.
5. **Guarded Role Changes:** Admins must be able to change roles and deactivate accounts, but we must prevent accidental lockout. A minimum of 2 active admins is enforced on the server-side to ensure the site always remains manageable.

## Alternatives Considered
- **Supabase Email Invites:** Rejected because it sends email-based sign-in links. We explicitly require Google OAuth as our identity provider, and we want to allow users to select their display name before logging in.
- **Subquery-based RLS Policies:** Rejected because they caused query timeouts and page load failures due to recursive policies when evaluating authenticated sessions.

## Consequences
- Administrators can generate invite links via the dashboard at `/admin/members/invites` and manage member status at `/admin/members`.
- The `invite_tokens` table acts as a single-use ledger (tracking `used_by` and `used_at`).
- Deactivated accounts are blocked from accessing the site within a single page transition due to real-time middleware validation.
