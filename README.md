# University Club Website and Member Portal Prototype

This repository contains the prototype for a modern university club website and member portal. Built on Next.js 14, TypeScript, Tailwind CSS, and Supabase (PostgreSQL + Auth), it features account linking, rating submissions, event tracking, a member gallery, and a Grammy.js-based Telegram bot integration.

---

## Getting Started

### Prerequisites

- [Node.js](https://nodejs.org) (v18 or higher recommended)
- A [Supabase](https://supabase.com) account and database instance
- A Google Cloud Console account (for Google OAuth)
- A Cloudflare account (for R2 storage bucket)
- A Telegram Bot token (from [@BotFather](https://t.me/BotFather))

*Note: Hosting on Vercel is recommended for the deployment phase, but it is not a strict prerequisite; you can deploy this Next.js app to any node-compatible hosting service.*

### Local Setup

1. **Clone the repository and install dependencies:**
   ```bash
   npm install
   ```

2. **Configure environment variables:**
   Copy the example environment file:
   ```bash
   cp .env.example .env.local
   ```
   Open `.env.local` and configure the following variables:
   - `NEXT_PUBLIC_SUPABASE_URL`: Your Supabase project URL.
   - `NEXT_PUBLIC_SUPABASE_ANON_KEY`: Your Supabase project Anonymous public key.
   - `SUPABASE_SERVICE_ROLE_KEY`: Your Supabase Service Role key (strictly server-side).
   - `TELEGRAM_BOT_TOKEN`: The API token obtained from @BotFather.
   - `NEXT_PUBLIC_SITE_URL`: Set to `http://localhost:3000` for local development.
   - `HEALTH_CHECK_SECRET`: A secret string used to secure the database wake-up endpoint. **You define this secret yourself** (invent any random secure string) and configure the same value in your hosting server environment variables and GitHub Action Secrets.
   
   **Cloudflare R2 Configuration:**
   - `CLOUDFLARE_R2_ACCOUNT_ID`: Your Cloudflare account ID.
   - `CLOUDFLARE_R2_ACCESS_KEY_ID`: Cloudflare R2 API token Access Key ID.
   - `CLOUDFLARE_R2_SECRET_ACCESS_KEY`: Cloudflare R2 API token Secret Access Key.
   - `CLOUDFLARE_R2_BUCKET_NAME`: The name of your R2 bucket.
   - `CLOUDFLARE_R2_PUBLIC_URL`: The public access URL of your R2 bucket (e.g. `https://pub-xxx.r2.dev`).

3. **Database Setup & Migrations:**
   You can push the local migrations located in `./supabase/migrations` directly to your Supabase PostgreSQL instance using the Supabase CLI or SQL Editor:
   ```bash
   supabase link --project-ref <your-project-id>
   supabase db push
   ```

4. **Run the development server:**
   ```bash
   npm run dev
   ```
   Open [http://localhost:3000](http://localhost:3000) in your browser to view the application.

## Service Configurations

### 1. Google OAuth Setup
The portal uses Supabase Auth with Google OAuth. No passwords are stored locally.
To configure this:
1. Go to the [Google Cloud Console](https://console.cloud.google.com/) and create a project.
2. Navigate to **APIs & Services** ➔ **OAuth consent screen** and configure the consent page.
3. Under **Credentials**, click **Create Credentials** ➔ **OAuth client ID**. Select *Web application*.
4. In your **Supabase Dashboard**, go to **Authentication** ➔ **Providers** ➔ **Google**.
5. Enable the Google provider, then copy the **Redirect URI** displayed at the top of the Google provider card.
6. Return to Google Cloud Console, and add this Redirect URI under **Authorized redirect URIs**.
7. Copy the **Client ID** and **Client Secret** generated by Google, paste them into the fields in the Supabase Dashboard, and save.

### 2. Cloudflare R2 Storage Setup
The member gallery, blog cover images, and event photos are uploaded directly to Cloudflare R2.
To configure this:
1. Log in to the Cloudflare dashboard and navigate to **R2**.
2. Click **Create bucket**, name your bucket, and click create.
3. In the bucket settings, click **Allow Access** under *Public Access* to generate a public URL, and paste it into `CLOUDFLARE_R2_PUBLIC_URL`.
   * **Development vs Production Domains:** For development and testing, you can use the default R2.dev subdomain (e.g. `https://pub-xxxxxx.r2.dev`). However, for production deployments, it is highly recommended to connect a custom domain (e.g., `assets.yourclub.org`) in Cloudflare bucket settings and update the environment variable accordingly to avoid rate limits or performance bottlenecks.
4. **CORS Policy:** Not required. Since uploads are handled server-side (the browser sends the file to our Next.js API route, which then uploads it to R2), the browser makes a **Same-Origin** request to your own domain. The browser never makes direct cross-origin calls to the R2 bucket, meaning CORS security checks are never triggered.
   * **Why we chose server-side uploads:** In addition to keeping R2 credentials secure, routing uploads through our Next.js API endpoint allows us to use the server-side `sharp` image library. Even if a user bypasses the client-side browser compression (e.g. using Postman or curl to upload a raw 20MB file or a disguised malicious payload), our backend server automatically sanitizes, validates, resizes, and converts it into a clean, optimized WebP before sending it to R2.
   * **Pre-Optimization Design:** Since images are already pre-optimized into WebP format at upload time (via both client-side Canvas and server-side Sharp), they are stored on R2 as lightweight assets. This enables us to serve them directly without running Vercel's CPU-intensive dynamic Next.js image optimization.
5. Go to the main R2 page, click **Manage R2 API Tokens**, and click **Create API token**. Set permissions to **Object Read & Write**, choose the appropriate bucket, and click generate.
6. Copy the access key and secret key details into `CLOUDFLARE_R2_ACCESS_KEY_ID` and `CLOUDFLARE_R2_SECRET_ACCESS_KEY`.

## Developer Account Promotion (Admin Role)

By default, any new user signing in via Google OAuth is created with the `member` role. To promote your account to `admin` or `committee` for local administration:

1. Sign in to the portal once using Google OAuth to trigger user creation in the database.
2. Log in to the Supabase Dashboard and open the **SQL Editor**.
3. Run the following SQL query to update your user profile:
   ```sql
   UPDATE public.users 
   SET role = 'admin' 
   WHERE email = 'your.email@domain.com';
   ```
4. Sign out and sign back in to the portal to refresh your session JWT, which embeds the new role.

## Review Rate Limiting Rules

To prevent spam, rating submissions are rate-limited:
- Users are restricted to a maximum of **30 rating submissions per calendar day (UTC)**.
- Counting is done based on rows created today.
- **Updates/Edits** to existing ratings (e.g., editing notes or updating a score on a previously rated title) **do not** count towards this daily limit.

## Telegram Bot Hook Integration

The portal integrates with a Telegram bot for member ratings.

1. **Get Bot Token**: Create a bot via [@BotFather](https://t.me/BotFather) and set `TELEGRAM_BOT_TOKEN`.
2. **Set up Webhook**: Register the API webhook handler URL with Telegram so it routes updates to Next.js.
   - **Alternative 1 (Via Browser GET):** Simply copy and paste the following URL into your browser address bar and press Enter (it will register successfully using a GET request):
     ```text
     https://api.telegram.org/bot<YOUR_TELEGRAM_BOT_TOKEN>/setWebhook?url=<YOUR_DEPLOYED_SITE_URL>/api/telegram
     ```
   - **Alternative 2 (Via curl POST):** Send a POST request using curl or Postman:
     ```bash
     curl -X POST "https://api.telegram.org/bot<YOUR_TELEGRAM_BOT_TOKEN>/setWebhook?url=<YOUR_DEPLOYED_SITE_URL>/api/telegram"
     ```
   *Note: Telegram webhooks require an HTTPS URL. For local testing, use a tunneling tool like `ngrok` (e.g., `ngrok http 3000`).*

## Deploying to Vercel

The portal is optimized for deployment on Vercel.

### Critical Production Configurations

1. **Latency Optimization (Vercel Region):**
   By default, Vercel places Serverless Functions in the USA (`iad1`). If your Supabase database is in Singapore (`ap-southeast-1`), this adds ~250ms of network latency. 
   - Change your Vercel Function region to **Singapore (`sin1`)** in Vercel under *Settings ➔ Functions ➔ Function Region*, then redeploy. This reduces query latency to under **5ms**.

2. **Environment Variables:**
   Add all keys configured in `.env.local` to Vercel's *Settings ➔ Environment Variables*. Note that building the Next.js bundle requires valid Supabase public keys to execute static page pre-generation.

3. **Vercel Payload Size Limitation (4.5MB):**
   Vercel serverless functions enforce a strict **4.5MB request body size limit**. 
   - While uploading a larger file (e.g. 7MB) works fine on **localhost** (since there is no gateway proxy limit locally), uploading files larger than 4.5MB on your deployed Vercel site would trigger a `413 Payload Too Large` error at the gateway.
   - **How it is resolved:** To prevent this, we have **already implemented client-side WebP compression** using HTML5 Canvas (`src/lib/image-client.ts`) inside the upload components. Even if a committee member selects a raw 10MB photo, it is automatically compressed down to < 400KB in the browser before being transmitted, fully bypassing this limit.

4. **Supabase Free-Tier Inactivity Workaround:**
   Supabase free tier databases pause after 1 week of inactivity. 
   - A weekly GitHub action workflow `.github/workflows/ping-db.yml` is included to trigger a lightweight query on `/api/health`.
   - Add your `HEALTH_CHECK_SECRET` as a GitHub Secret (`HEALTH_CHECK_SECRET`) in your repository.

5. **Next.js Image Optimization Bypass (`unoptimized`):**
   Vercel’s Hobby/Free tier limits dynamic Next.js image optimization to **1,000 source images per month**. 
   - **How it is resolved:** To prevent hitting this limit and incurring fees/errors, all rendering uses the Next.js `<Image>` component with the `unoptimized` attribute. This bypasses Vercel's dynamic runtime optimizer completely. Since our upload pipeline has already pre-compressed the image, we serve the lightweight WebP directly from R2, while still benefiting from `<Image>`'s automatic viewport lazy-loading and Cumulative Layout Shift (CLS) prevention (which is a key Google Web Vitals/SEO ranking factor).
